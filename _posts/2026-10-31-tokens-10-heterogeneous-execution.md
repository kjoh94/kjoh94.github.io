> **한 줄 핵심** — 가속기(NPU/GPU)는 행렬 곱을 아주 빠르고 전력 효율 좋게 하지만, **모든 연산을 다 하진 못해요.** 그래서 토크나이저·특수 연산·샘플링은 CPU가, 무거운 행렬 곱은 가속기가 맡아요. 성능은 결국 **경계를 몇 번, 얼마나 큰 데이터를 들고 넘느냐**에서 갈려요.

## 0. 큰 루프에서 어디에 꽂히나

![CPU·가속기 분담이 꽂히는 자리](/assets/img/posts/tokens-10-heterogeneous-execution/fig01.jpg)

*그림 1. 이 장치는 슬롯 하나가 아니라 루프 전체의 바닥이에요. 한 바퀴 안에서 CPU의 입구·출구 일과 가속기의 행렬 곱이 번갈아 일어나고, 그 경계를 넘는 횟수가 성능을 정해요.*

---

## 1. 비유: 공장 라인

용접처럼 똑같은 동작을 수만 번 반복하는 일은 로봇이 해요. 빠르고 지치지 않아요. 하지만 처음 보는 부품 검수나 포장 예외 처리는 사람이 해요. 로봇은 프로그램된 동작만 할 수 있거든요. 가속기가 로봇, CPU가 사람이에요.

![CPU와 가속기의 분업](/assets/img/posts/tokens-10-heterogeneous-execution/fig02.jpg)

*그림 2. CPU 레인에서 토크나이저와 임베딩 조회를 하고, 가속기 레인에서 Attention·FFN을 N층 반복한 뒤, 가속기가 모르는 연산과 샘플링을 CPU가 하고 다음 바퀴로 돌아가요.*

---

## 2. 왜 다 가속기에서 하지 않나

| 이유 | 설명 |
|---|---|
| **지원 연산의 한계** | 가속기는 정해진 연산 집합(행렬 곱, 컨볼루션, 몇 가지 활성 함수)에 최적화돼요. 새 모델의 새 활성 함수·정규화·RoPE 변형은 아직 모를 수 있어요. |
| **고정 shape** | 2편의 사전 컴파일은 보통 shape를 고정해요. 길이가 매번 다른 문자열 처리나 분기 많은 로직은 안 맞아요. |
| **문자열과 제어 흐름** | 토크나이저, stop 검사, HTTP, 스케줄러는 원래 CPU 일이에요. |
| **메모리 용량** | 가속기 메모리에 모델이 다 안 들어가면 일부 층을 CPU 쪽에 둬야 해요. |

그래서 새 모델이 나오면 보통 이렇게 흘러가요. **처음엔 모르는 연산만 CPU로 폴백해서 일단 돌린다 → 자주 쓰이면 가속기용으로 이식한다.**

---

## 3. 경계를 넘을 때마다 세금

CPU ↔ 가속기를 오갈 때마다 두 가지 비용이 들어요.

1. **데이터 복사**: 활성값을 반대편 메모리로 옮겨요. (통합 메모리 칩이면 작아지지만 0은 아니에요.)
2. **동기화 대기**: 한쪽이 끝날 때까지 다른 쪽이 기다려요. 런치 오버헤드도 붙어요.

![경계 횟수 비교](/assets/img/posts/tokens-10-heterogeneous-execution/fig03.jpg)

*그림 3. 위쪽은 층마다 미지원 연산 하나 때문에 CPU를 다녀와 경계를 12번 넘고, 아래쪽은 미지원 연산을 대체 구현해 가속기 안에 묶어 경계를 2번만 넘어요. 빨간 선 하나하나가 복사와 대기예요.*

Decode 한 바퀴는 수십 ms예요. 층이 32개인데 층마다 경계를 두 번 넘고 한 번에 0.2ms씩 든다면, **바퀴당 13ms가 세금**이에요. 가속기가 아무리 빨라도 이 세금이 남아요.

| 해법 | 하는 일 |
|---|---|
| 대체 구현 | 미지원 연산을 지원 연산 조합으로 다시 쓰기 (예: GELU 근사, 나눗셈 → 곱셈) |
| 연산 융합 | 작은 연산 여러 개를 가속기 커널 하나로 |
| 경계 위치 옮기기 | 경계를 루프 안쪽에서 바깥쪽(입구·출구)으로 |
| 통합 메모리 | 복사 대신 같은 메모리를 공유 |
| 샘플링 이식 | 로짓 전체(수만 개) 대신 고른 토큰 1개만 넘기기 |

마지막 줄이 의외로 커요. 어휘가 15만 개면 로짓은 바퀴마다 15만 개 숫자예요. 가속기에서 top-k까지 하고 몇십 개만 넘기면 전송이 수천 분의 1로 줄어요.

---

## 4. 메모리가 모자랄 때: 층 나눠 싣기

![층 오프로딩과 속도](/assets/img/posts/tokens-10-heterogeneous-execution/fig04.jpg)

*그림 4. 32층 중 몇 층을 가속기에 올리느냐에 따른 토큰/초 예시예요. Decode 속도는 가장 느린 층이 결정해서, 마지막 몇 층까지 올려야 확 빨라져요.*

llama.cpp의 `-ngl`(가속기에 올릴 층 수)이 대표적이에요. 직관과 다른 점이 하나 있어요. **절반만 올리면 절반만큼 빨라지는 게 아니에요.** Decode는 층을 차례로 지나가니까, CPU에 남은 층의 메모리 대역폭이 전체 바퀴 시간을 끌고 내려가요. 그래서 1편의 양자화로 모델을 줄여 **전부 올리는 것**이 대개 더 나아요.

KV 캐시도 마찬가지예요. 6편의 스왑처럼 CPU 메모리로 내릴 수는 있지만, 매 바퀴 읽는 데이터라 자주 오가면 느려져요.

## 5. 무엇을 어디에 두나

![배치 출발점 표](/assets/img/posts/tokens-10-heterogeneous-execution/fig05.jpg)

*그림 5. 토크나이즈·스케줄러·HTTP는 CPU, 행렬 곱과 KV 캐시는 가속기, 새 특수 연산은 처음엔 CPU 폴백 뒤 이식, 샘플링은 작지만 매 바퀴라 왕복 비용을 보고 정해요.*

측정은 이 순서로 하면 좋아요.

1. **연산별 위치 프로파일**: 어떤 연산이 어디서 도는지 목록부터.
2. **경계 횟수**: 바퀴당 몇 번 넘나.
3. **복사 바이트**: 한 번에 얼마나 들고 넘나.
4. **가장 느린 구간**: 개선은 거기서부터.

---

## 6. 실패 모드

| 증상 | 흔한 원인 |
|---|---|
| 가속기 이용률이 낮은데 느림 | 경계 핑퐁, CPU 쪽 연산이 병목 |
| 새 모델만 유독 느림 | 미지원 연산 CPU 폴백 |
| 긴 문맥에서 급격히 느려짐 | KV 캐시가 가속기 메모리 밖으로 밀림 |
| CPU 사용률 100% | 토크나이저·샘플링·디토크나이즈가 배치 크기에 비례해 늘어남 |
| 전력 소비가 예상보다 큼 | CPU가 쉬지 않고 대기 루프 |

## 7. 시리즈를 닫으며: 한 장면으로

열 가지 장치를 루프 위에 다시 올려 볼게요.

| # | 장치 | 꽂히는 곳 | 주로 줄이는 것 |
|---|---|---|---|
| 1 | 양자화 | 가중치 | 메모리, Decode 시간 |
| 2 | 사전 컴파일 | 루프 시작 전 | 실행 오버헤드 |
| 3 | 샘플링 | 매 바퀴 출구 | (품질·다양성 조절) |
| 4 | KV 캐시 | Decode 매 바퀴 | 재계산 |
| 5 | Prefix 재사용 | Prefill 입구 | TTFT, 비용 |
| 6 | 연속 배치 | Decode 전체 | 토큰당 비용 |
| 7 | 청크 Prefill | Prefill ↔ Decode 사이 | 끊김(p99 TPOT) |
| 8 | OpenAI 호환 API | 현관문 | 연결 비용(채택) |
| 9 | 스트리밍 | 출구 → 사용자 | 체감 지연 |
| 10 | CPU·가속기 분담 | 하드웨어 바닥 | 경계 세금, 전력 |

증상을 보면 루프의 위치를 떠올리고, 위치를 보면 장치를 고르면 돼요. 프롤로그에서 말한 세 칸짜리 사고, **증상 → 위치 → 장치**가 이 표 한 장이에요.

## 직접 만져보기

```bash
# llama.cpp: 가속기에 올리는 층 수를 바꿔 가며 토큰/초 비교
for n in 0 8 16 24 99; do
  ./llama-bench -m model-q4_k_m.gguf -ngl $n -p 0 -n 128
done
```

`-ngl`을 늘려 가며 그래프를 그려 보면, 위 그림 4처럼 끝에서 확 꺾이는 곡선이 직접 나와요.
