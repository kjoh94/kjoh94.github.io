> **한 줄 핵심** — 양자화는 가중치 하나를 표현하는 비트 수를 줄여(16비트 → 8비트 → 4비트) **모델을 작게 만드는 기술**이에요. Decode는 "가중치를 읽어 오는 속도"에 묶여 있으니, 모델이 작아지면 토큰이 그대로 빨라져요. 대신 너무 깎으면 숫자가 틀리기 시작해요.

## 0. 큰 루프에서 어디에 꽂히나

![양자화가 꽂히는 자리](/assets/img/posts/tokens-01-quantization/fig01.jpg)

*그림 0. 양자화는 루프의 **가중치 자체**에 꽂혀요. Prefill과 Decode 모두 같은 가중치를 쓰지만, 효과가 가장 크게 드러나는 곳은 매 바퀴마다 가중치 전체를 다시 읽어야 하는 **Decode**예요.*

---

## 1. 비유: JPEG처럼 "티 안 나게" 줄이기

휴대폰 사진 원본(RAW)은 수십 MB인데, JPEG로 저장하면 몇 MB로 줄어요. 확대해서 뜯어보면 미세한 디테일이 사라졌지만, 보통 눈으로는 차이를 거의 못 느끼죠. 그런데 압축률을 극단적으로 올리면 블록이 깨지고 색이 번져요.

양자화도 똑같아요.

| 사진 | 모델 |
|---|---|
| RAW 원본 | FP16/BF16 가중치 |
| JPEG 품질 90 | INT8 |
| JPEG 품질 60 | INT4 (Q4_K_M 등) |
| JPEG 품질 10 (깍두기 노이즈) | 2~3비트 과도 양자화 |

핵심은 **"사람(또는 과제)이 알아챌 만큼 망가지기 직전까지"** 줄이는 거예요.

---

## 2. 숫자를 얇게 깎는다는 게 정확히 뭘까

### 비트 수 = 표현할 수 있는 칸의 개수

- FP16: 16비트 → 약 65,000가지 값(부동소수점이라 범위도 넓음)
- INT8: 8비트 → 256칸
- INT4: 4비트 → **16칸**

INT4라면 가중치 하나가 "16개의 눈금 중 하나"로만 표현돼요. 연속적이던 값을 계단으로 바꾸는 거예요.

### 숫자 예시: 가중치 8개를 INT4로

원래 가중치(FP16)가 이렇다고 해 볼게요.

```text
w = [ 0.82, -0.31, 0.05, -0.77, 0.44, 0.12, -0.03, 0.69 ]
```

**블록 단위 대칭 양자화**를 해 보면,

```text
1) 블록의 최대 절댓값: max|w| = 0.82
2) INT4 대칭 범위: -7 ~ +7  → scale = 0.82 / 7 ≈ 0.117
3) q = round(w / scale)
   q = [ 7, -3, 0, -7, 4, 1, 0, 6 ]          ← 4비트 정수로 저장
4) 복원: w' = q × scale
   w' = [ 0.82, -0.35, 0.00, -0.82, 0.47, 0.12, 0.00, 0.70 ]
5) 오차: |w - w'| = [0, 0.04, 0.05, 0.05, 0.03, 0, 0.03, 0.01]
```

- 저장하는 것: 정수 8개(4비트씩 = 4바이트) + scale 1개(2바이트)
- 원래: 8개 × 2바이트 = 16바이트 → **약 6바이트로**

작은 값(0.05, -0.03)은 0으로 뭉개졌어요. 이게 양자화 오차예요. 블록을 작게(예: 32개씩) 나누고 블록마다 scale을 따로 두는 이유는, **큰 값 하나 때문에 블록 전체의 눈금이 성겨지는 것**을 막기 위해서예요.

![눈금과 스냅](/assets/img/posts/tokens-01-quantization/fig02.jpg)

*그림 1. 비트가 줄면 눈금이 성겨지고, 각 가중치는 가장 가까운 눈금으로 스냅돼요. 금색 선분이 양자화 오차예요.*

### 메모리는 얼마나 줄어들까

| 모델 | FP16 | INT8 | INT4 (Q4_K_M, 실효 ~4.8비트) |
|---|---|---|---|
| 8B | 16 GB | 8 GB | ~4.9 GB |
| 14B | 28 GB | 14 GB | ~8.5 GB |
| 70B | 140 GB | 70 GB | ~42 GB |

INT4가 정확히 1/4이 안 되는 이유는 scale·zero-point 같은 **메타데이터**와 일부 민감한 층(임베딩, 출력층)을 더 높은 정밀도로 남겨 두기 때문이에요.

![메모리와 Decode 속도](/assets/img/posts/tokens-01-quantization/fig03.jpg)

*그림 2. 메모리 막대가 짧아질수록, 같은 대역폭에서 Decode TPS 숫자는 커져요.*

## 3. 왜 작아지면 빨라질까: Decode는 "읽기" 병목

프롤로그에서 본 공식을 다시 꺼내 볼게요.

```text
Decode 이론 상한 TPS ≈ 메모리 대역폭 / 모델 크기
```

대역폭 200 GB/s 기기(고급 노트북·엣지 보드 수준)에서 8B 모델이라면,

| 형식 | 크기 | 이론 상한 TPS | 실제 체감(대략 60~70%) |
|---|---|---|---|
| FP16 | 16 GB | 12.5 | ~8 |
| INT8 | 8 GB | 25 | ~16 |
| Q4_K_M | 4.9 GB | 41 | ~27 |

연산량은 그대로인데도(오히려 복원 계산이 살짝 추가되는데도) 빨라져요. 계산 유닛은 원래 놀고 있었고, **책을 나르는 트럭이 문제였기 때문**이에요.

반면 **Prefill**은 연산 병목이라, 가중치만 INT4로 줄이고 계산을 FP16으로 하면(weight-only 양자화) Prefill은 크게 빨라지지 않을 수 있어요. 활성값까지 INT8/FP8로 계산하는 방식(W8A8 등)이어야 Prefill도 빨라져요.

| 방식 | 무엇을 줄이나 | 주로 빨라지는 곳 | 예시 |
|---|---|---|---|
| Weight-only (W4A16, W8A16) | 가중치만 | Decode | GGUF Q4_K_M, AWQ, GPTQ |
| Weight+Activation (W8A8, FP8) | 가중치+활성값 | Prefill + Decode | SmoothQuant, FP8 (최신 GPU) |
| KV 캐시 양자화 | 대화 메모 | 긴 컨텍스트 메모리 | llama.cpp `-ctk q8_0`, vLLM `kv_cache_dtype=fp8` |

## 4. 대표 포맷 둘러보기

### GGUF와 Q4_K_M (llama.cpp / Ollama)

llama.cpp 생태계의 파일 포맷이 **GGUF**예요. 파일 이름 끝의 꼬리표가 양자화 방식을 알려 줘요.

| 태그 | 실효 비트 | 8B 크기(대략) | 느낌 |
|---|---|---|---|
| F16 | 16 | 16 GB | 원본 |
| Q8_0 | ~8.5 | 8.5 GB | 원본과 거의 구분 불가 |
| Q6_K | ~6.6 | 6.6 GB | 매우 안전 |
| Q5_K_M | ~5.7 | 5.7 GB | 안전 |
| **Q4_K_M** | ~4.8 | 4.9 GB | **가성비 기본값** |
| Q3_K_M | ~3.9 | 4.0 GB | 눈에 띄는 열화 시작 |
| Q2_K | ~3.0 | 3.2 GB | 실험용 |

`K`는 "k-quant"(블록을 슈퍼블록으로 묶어 scale도 다시 양자화하는 방식), `_M`/`_S`/`_L`은 민감한 층에 비트를 얼마나 더 주는지(Medium/Small/Large) 정도로 이해하면 돼요.

### AWQ / GPTQ (vLLM, Hugging Face)

GPU 서빙 쪽에서는 **AWQ**(Activation-aware Weight Quantization)와 **GPTQ**가 흔해요.

- **AWQ 아이디어**: "모든 가중치가 똑같이 중요하지 않다." 활성값이 크게 곱해지는 소수(~1%)의 채널이 결과를 좌우하니, 그 채널을 scale로 보호한 뒤 4비트로 깎아요.
- **GPTQ 아이디어**: 하나씩 양자화하면서 생긴 오차를 아직 양자화 안 한 가중치들이 조금씩 메꾸도록 보정해요.
- 둘 다 **보정용 데이터(calibration set)** 몇 백 문장이 필요해요. 이 데이터가 실제 사용 분야와 너무 다르면 품질이 떨어질 수 있어요.

## 5. 실패 장면: 너무 얇게 깎으면

같은 8B 모델에 같은 질문을 던져 볼게요. (아래 출력은 경향을 보여 주기 위한 **예시**예요.)

> **질문**: "1,234 × 56은? 그리고 세종대왕이 한글을 반포한 해는?"

| 형식 | 답변 예시 | 문제 |
|---|---|---|
| FP16 | "69,104입니다. 훈민정음은 1446년에 반포되었어요." | — |
| Q4_K_M | "69,104입니다. 훈민정음은 1446년에 반포되었어요." | 거의 동일 |
| Q3_K_S | "69,140입니다. 훈민정음은 1446년에…" | **숫자 자릿수 오류** |
| Q2_K | "약 6만 9천입니다. 한글은 1443년에 반포되어 세종 25년…" | 숫자 뭉개짐 + **사실 혼동(창제/반포)** |

과도한 양자화의 전형적인 증상은 이래요.

1. **정확한 숫자·코드·고유명사가 먼저 무너져요.** 일반 대화는 멀쩡해 보여서 더 위험해요.
2. **환각이 늘어요.** 확신에 찬 말투는 그대로인데 내용이 틀려요.
3. **반복 루프**: 같은 문장을 계속 되풀이하거나 이상한 토큰이 섞여요.
4. **긴 추론에서 누적 붕괴**: 짧은 답은 괜찮은데 10단계 풀이에서 중간에 길을 잃어요.
5. **작은 모델일수록 더 취약**: 70B의 Q4보다 1B의 Q4가 훨씬 많이 망가져요. 큰 모델은 "여유분(redundancy)"이 많거든요.

### 잘못된 직관: "4비트면 품질도 1/4이 된다"

비트를 1/4로 줄였다고 품질이 1/4이 되는 게 아니에요. 품질 곡선은 **직선이 아니라 절벽형**이에요. 8 → 5비트 구간은 거의 평평하다가, 4비트 아래쪽에서 갑자기 꺾여요. 그래서 "4비트 근처까지는 거의 공짜, 그 아래는 비쌈"이 실무 감각이에요.

또 하나의 흔한 오해는 **"같은 메모리라면 큰 모델의 Q4보다 작은 모델의 FP16이 낫다"** 인데, 대체로 반대예요. 메모리 8GB가 있다면 8B FP16(16GB, 안 들어감)이나 4B FP16(8GB)보다 **14B Q4(~8.5GB)** 가 더 똑똑한 경우가 많아요.

![비트 수에 따른 품질과 속도](/assets/img/posts/tokens-01-quantization/fig04.jpg)

*그림 3. 품질 곡선은 절벽형, 속도 곡선은 우상향. 금색 띠(4~5비트)가 대부분의 사람이 고르는 지점이에요.*

## 6. 정상 장면: 잘 깎으면

- 8B 모델을 **Q4_K_M(4.9GB)** 으로 바꿔 8GB 노트북에서 돌리고, 일상 대화·요약·번역에서 원본과 차이를 거의 못 느껴요.
- 70B 모델을 **AWQ 4비트(~40GB)** 로 바꿔 80GB GPU 한 장에 올리고, 남는 메모리를 KV 캐시와 동시 요청(배칭)에 써요.
- 엣지 가속기에서는 INT8/INT4 전용 연산기가 있어, 양자화된 모델이 **메모리와 전력 모두** 아껴요. 많은 엣지 런타임(예: Rockchip RKLLM, Qualcomm QAIRT)이 양자화를 사실상 기본 전제로 삼아요.

### 실무 체크리스트

1. 먼저 Q8로 "원본과 같은지" 확인 → 기준선 잡기
2. Q5_K_M, Q4_K_M로 내려가며 **내 과제(숫자? 코드? 대화?)** 로 비교
3. 퍼플렉서티(perplexity) 차이가 원본 대비 몇 % 이내인지 확인
4. 숫자·코드가 중요하면 한 단계 높은 비트를, 대화 위주라면 Q4를

## 7. 트레이드오프 표

| 축 | FP16 | INT8 / Q8 | INT4 / Q4_K_M | 3비트 이하 |
|---|---|---|---|---|
| 메모리 (8B) | 16 GB | ~8.5 GB | ~4.9 GB | ~3~4 GB |

| 품질 손실 | 0 | 거의 0 | 작음 | 큼 |
| 숫자/코드 정확도 | 기준 | 거의 동일 | 약간 위험 | 위험 |
| 준비 비용 | 없음 | 낮음 | 보정 데이터(AWQ/GPTQ) | 높음 |
| 추천 상황 | 연구·기준선 | 품질 우선 서빙 | 로컬·엣지 기본값 | 실험 |

## 8. 직접 만져보기

### A. llama.cpp: 같은 모델을 Q8과 Q4로 만들어 크기·속도 비교

```bash
# 1) llama.cpp 받기 & 빌드
git clone https://github.com/ggml-org/llama.cpp
cd llama.cpp && cmake -B build && cmake --build build -j

# 2) Hugging Face 모델을 GGUF(F16)로 변환
python convert_hf_to_gguf.py /path/to/hf-model --outtype f16 --outfile model-f16.gguf

# 3) 양자화
./build/bin/llama-quantize model-f16.gguf model-Q8_0.gguf   Q8_0
./build/bin/llama-quantize model-f16.gguf model-Q4_K_M.gguf Q4_K_M

# 4) 크기 비교
ls -lh model-*.gguf

# 5) 속도 비교 (pp = Prefill, tg = Decode)
./build/bin/llama-bench -m model-Q8_0.gguf   -p 512 -n 128
./build/bin/llama-bench -m model-Q4_K_M.gguf -p 512 -n 128

# 6) 품질 비교 (낮을수록 좋음)
./build/bin/llama-perplexity -m model-Q4_K_M.gguf -f wiki.test.raw
```

**관찰 포인트**: `tg128`(Decode)은 Q4가 확실히 빠르고, `pp512`(Prefill)는 차이가 상대적으로 작을 거예요. 0편에서 본 "Decode = 읽기 병목"이 숫자로 확인돼요.

### B. Ollama: 태그만 바꿔 보기

```bash
ollama pull llama3.1:8b-instruct-q8_0
ollama pull llama3.1:8b-instruct-q4_K_M
ollama list            # SIZE 열 비교
ollama run llama3.1:8b-instruct-q4_K_M --verbose "1234 × 56은?"
```

(정확한 태그 이름은 Ollama 라이브러리 페이지에서 확인하세요.)

### C. vLLM: AWQ 모델 서빙

```bash
pip install vllm
vllm serve Qwen/Qwen2.5-7B-Instruct-AWQ --quantization awq
```
