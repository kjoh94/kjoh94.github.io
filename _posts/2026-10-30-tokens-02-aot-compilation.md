> **한 줄 핵심** — 사전 컴파일(AOT, Ahead-Of-Time)은 범용 모델 그래프를 **특정 칩이 가장 잘 실행하는 형태로 미리 번역해 파일로 저장**해 두는 거예요. 실행할 때는 번역 없이 바로 돌리니 시작이 빠르고, 속도가 예측 가능해져요. 대신 그 번역본은 **그 칩, 그 설정에서만** 통해요.

## 0. 큰 루프에서 어디에 꽂히나

![사전 컴파일이 꽂히는 자리](/assets/img/posts/tokens-02-aot-compilation/fig01.jpg)

*그림 0. 사전 컴파일은 루프 **안**이 아니라 루프가 **시작되기 전**에 꽂혀요. 한 번 번역해 두면, 그 뒤의 모든 Prefill과 Decode 바퀴가 그 번역본 위에서 돌아요.*

---

## 1. 비유: 동시통역 vs 미리 번역해 둔 책

외국 소설을 읽는 두 가지 방법이 있어요.

- **동시통역사(JIT, 실행 중 번역)**: 한 문장씩 읽을 때마다 통역사가 그 자리에서 번역해 줘요. 어떤 책이 와도 대응할 수 있지만, 처음엔 느리고 통역사 컨디션(캐시, 워밍업)에 따라 속도가 들쭉날쭉해요.
- **번역서(AOT, 미리 번역)**: 출판사가 몇 주 걸려 번역하고 교정까지 해서 책으로 찍어 둬요. 독자는 펼치자마자 바로 술술 읽어요. 대신 **한국어판은 한국어 독자에게만** 쓸모 있고, 원서가 개정되면 다시 번역해야 해요.

여기서 "언어"가 바로 **칩**이에요. GPU 세대마다, NPU/가속기 종류마다 잘하는 연산, 메모리 구조, 지원하는 숫자 형식이 달라요. 사전 컴파일은 **그 칩의 모국어로 된 번역서**를 만드는 일이에요.

## 2. 범용 모델 → 컴파일러 → 칩 전용 파일 → 런타임

```text
[범용 모델]                [컴파일러]                     [칩 전용 파일]        [런타임]
PyTorch / HF 가중치   →   그래프 분석·융합·양자화   →   엔진/바이너리     →   로드 → 실행
ONNX 그래프               타일링·메모리 계획              (칩·형상 고정)        (Prefill/Decode 루프)
                          커널 선택(튜닝)
```

컴파일러가 하는 일을 하나씩 풀어 볼게요.

| 단계 | 무엇을 하나 | 예시 |
|---|---|---|
| 그래프 캡처 | 모델을 "연산 노드 + 데이터 흐름" 그래프로 펼침 | `MatMul → Add → RMSNorm → SiLU …` |
| 연산 융합(fusion) | 붙어 있는 작은 연산을 하나의 커널로 합침 | `MatMul + Bias + GELU` → 한 커널 |
| 정밀도 결정 | 층별로 FP16/INT8/INT4 선택 (1편 양자화와 연결) | 어텐션은 FP16, FFN은 INT4 |
| 메모리 계획 | 중간 텐서를 어디에 언제 둘지 미리 배치 | 온칩 SRAM 재사용 계획 |
| 타일링 | 큰 행렬을 칩의 연산 단위 크기로 쪼갬 | 128×128 타일 |
| 커널 선택/튜닝 | 같은 연산의 여러 구현 중 이 칩에서 제일 빠른 것 선택 | 후보 20개 벤치마크 |
| 직렬화 | 결과를 파일로 저장 | `.engine`, `.plan`, 칩별 바이너리 |

![범용 그래프에서 칩 전용 IR로](/assets/img/posts/tokens-02-aot-compilation/fig02.jpg)

*그림 1. 범용 그래프(왼쪽 12개 노드)가 컴파일을 거쳐 칩 전용 IR(오른쪽 5개 노드)로 바뀌는 과정. 노드가 합쳐지고, 정밀도가 칠해지고, 칩의 연산 격자 위에 배치돼요.*

### 숫자 예시: 융합 하나가 아끼는 것

토큰 하나를 Decode할 때 FFN 블록의 활성값이 4,096개(FP16, 8KB)라고 해 볼게요.

```text
융합 전:  MatMul → (메모리에 쓰기) → Add → (쓰기) → SiLU → (쓰기) → Mul
          중간 결과를 메모리에 3번 쓰고 3번 다시 읽음 → 8KB × 6 = 48KB 왕복
          커널 실행(launch) 4번 × 약 5μs = 20μs 오버헤드

융합 후:  [MatMul+Add+SiLU+Mul] 한 커널
          중간 결과는 레지스터/온칩 메모리에 머묾 → 왕복 ≈ 0
          커널 실행 1번 = 5μs
```

층이 32개라면 토큰당 오버헤드만 대략 32 × 15μs ≈ 0.5ms 절약이에요. 30 tok/s(토큰당 33ms)에서는 1.5% 정도지만, 작은 모델·빠른 칩에서 토큰당 5ms라면 **10%** 가 돼요. 작은 연산이 많은 엣지 환경일수록 융합의 효과가 커져요.

## 3. JIT vs AOT 한눈에 비교

| | JIT (실행 중 컴파일/해석) | AOT (사전 컴파일) |
|---|---|---|
| 번역 시점 | 첫 실행 시, 혹은 매번 | 배포 전 한 번 |
| 첫 실행(콜드 스타트) | 느림 (워밍업 필요) | 빠름 (로드만) |
| 실행 속도 예측성 | 형상 변화 시 재컴파일로 튐 | 일정함 |
| 유연성 | 높음 (아무 모델/형상) | 낮음 (정해진 칩·형상·정밀도) |
| 배포 파일 | 범용 모델 | 칩마다 별도 파일 |
| 대표 예 | PyTorch eager, `torch.compile`, XLA JIT | TensorRT 엔진, Qualcomm QAIRT 컨텍스트 바이너리, Rockchip RKLLM 모델 |
| 어울리는 곳 | 연구, 빠르게 바뀌는 서버 | 엣지·모바일·고정 서비스 |

### 공개 스택을 일반화해서 보면

- **TensorRT / TensorRT-LLM**: ONNX나 HF 체크포인트를 받아 GPU 세대에 맞춘 **engine**을 빌드해요. 최대 배치, 최대 입력 길이 같은 형상 범위를 빌드 때 정해요. 다른 세대 GPU로 옮기면 보통 다시 빌드해야 해요.
- **ONNX Runtime + Execution Provider(EP)**: 같은 ONNX 그래프를 받아 CUDA, TensorRT, QNN, CoreML 등 **EP**에 "이 노드는 네가 맡아"라고 분배해요. EP가 모르는 노드는 CPU로 넘겨요(아래 실패 장면 참고).
- **Qualcomm QAIRT**: 모델을 Hexagon NPU용 바이너리로 변환·양자화해 휴대폰 위에서 실행해요.
- **Rockchip RKLLM**: HF 모델을 RK 계열 NPU용 파일로 변환(양자화 포함)한 뒤, 보드의 런타임이 로드해 실행해요.
- **llama.cpp**: 전통적 의미의 "AOT 컴파일러"는 아니지만, 비슷한 철학이 있어요. 변환(`convert_hf_to_gguf.py`) → 양자화(`llama-quantize`) 단계에서 **실행에 맞는 형태로 미리 굳혀 두고**, 실행 시 백엔드(CUDA, Metal, Vulkan, CPU SIMD)별로 최적 커널을 골라 계산 그래프를 구성해요.

공통 패턴은 같아요: **"실행 시간에 고민할 것을 배포 전으로 최대한 끌어온다."**

## 4. 실패 장면: 칩이 모르는 op를 만나면

컴파일러는 그래프의 모든 노드를 칩의 언어로 번역하려고 해요. 그런데 칩이 **모르는 연산(unsupported op)** 이 나오면 어떻게 될까요? 결과는 대체로 세 가지 중 하나예요.

| 상황 | 무슨 일이 생기나 | 사용자 체감 |
|---|---|---|
| ① 컴파일 실패 | "Unsupported operator: XXX" 에러로 빌드 중단 | 배포 자체가 안 됨 |
| ② 런타임 폴백(fallback) | 그 노드만 CPU로 보내 실행 | **돌긴 도는데 이상하게 느림** |
| ③ 조용한 근사 | 비슷한 연산으로 대체(예: 근사 활성화 함수) | 숫자가 미묘하게 달라짐 |

### ②가 제일 무서운 이유: 폴백의 숫자

32층 모델에서, 층마다 하나씩 있는 새로운 활성화 함수(칩이 지원 안 함)가 CPU로 폴백된다고 해 볼게요.

```text
층당 흐름:  [가속기] MatMul → (가속기→CPU 복사) → [CPU] 새 활성화 → (CPU→가속기 복사) → [가속기] MatMul
층당 추가 비용: 복사 2회 × 0.2ms + CPU 연산 0.3ms ≈ 0.7ms
32층 × 0.7ms ≈ 22ms / 토큰

원래 토큰당 20ms(50 tok/s) → 42ms(약 24 tok/s)
```

연산 하나 때문에 **속도가 절반**이 돼요. 그래프 전체가 가속기 안에서 머물러야 빠른데, 중간중간 칩 밖으로 나갔다 들어오면서 "섬"이 쪼개지는 거예요.

![폴백 지그재그](/assets/img/posts/tokens-02-aot-compilation/fig03.jpg)

*그림 2. 칩이 모르는 연산(금색 "?")을 만날 때마다 데이터가 CPU로 내려갔다 올라와요. 이 지그재그가 폴백의 진짜 비용이에요.*

### 또 다른 실패: 형상(shape) 고정

AOT 엔진은 흔히 "최대 입력 길이 2,048, 최대 배치 8" 같은 범위를 빌드 때 정해요. 그런데 사용자가 8,000토큰 문서를 넣으면?

- 에러로 거절하거나,
- 잘라서(truncate) 앞부분만 보거나,
- 범위를 넓혀 **다시 빌드**해야 해요.

JIT 세계에선 그냥 돌아갔을 요청이, AOT 세계에선 **설계 시점의 약속**을 벗어나면 막혀요.

### 잘못된 직관: "컴파일하면 무조건 빨라진다"

컴파일은 "빨라질 기회"를 주는 거지, 보장이 아니에요.

- 지원 안 되는 op가 많으면 폴백 때문에 **오히려 느려질 수** 있어요.
- 빌드 때 가정한 형상(예: 배치 1)과 실제 사용(배치 16)이 다르면, 최적 커널이 아닌 걸로 돌아요.
- 컴파일러가 적극적으로 정밀도를 낮추면 빨라지는 대신 **품질이 조용히 떨어질** 수 있어요(1편의 양자화 실패와 연결).

그래서 컴파일 후에는 항상 **"속도 + 정확도" 둘 다** 원본과 비교해야 해요.

## 5. 정상 장면: 잘 컴파일되면

- 엣지 보드가 부팅 후 **모델 로드만 1~2초**, 첫 요청부터 바로 일정한 TPS가 나와요. 워밍업이 필요 없어요.
- 요청마다 TPS 편차가 작아서, 음성 비서처럼 **실시간 응답 예산(예: 300ms 안에 첫 토큰)** 을 맞추기 쉬워요.
- 그래프 전체가 가속기 안에서 돌아 CPU는 다른 일(음성 인식, UI)에 쓸 수 있어요.
- 같은 엔진 파일을 같은 기종 수천 대에 그대로 배포할 수 있어요.

### 컴파일 전후 체감(예시 숫자)

| 지표 | 범용 실행(JIT/eager) | 사전 컴파일 엔진 |
|---|---|---|
| 콜드 스타트 | 15s (첫 요청 워밍업 포함) | 2s |
| TTFT (512 토큰) | 0.6s | 0.35s |
| Decode TPS | 22 | 30 |
| TPS 편차 | ±25% | ±3% |
| 새 모델 적용 | 바로 | 재컴파일 필요(수 분~수십 분) |

(숫자는 경향을 보여 주는 예시예요. 실제 차이는 모델·칩·도구에 따라 크게 달라요.)

![JIT와 AOT 타임라인](/assets/img/posts/tokens-02-aot-compilation/fig04.jpg)

*그림 3. AOT는 비용을 "배포 전"으로 옮겨요. 그 대가로 실행 타임라인은 짧고 규칙적이 돼요.*

## 6. 트레이드오프 표

| 얻는 것 | 내주는 것 |
|---|---|
| 빠른 콜드 스타트 | 빌드 시간(수 분~수십 분) |
| 일정하고 예측 가능한 지연 | 형상·배치 범위가 고정됨 |
| 연산 융합·칩 전용 커널로 속도 향상 | 칩/드라이버/도구 버전에 묶임 |
| CPU 부담 감소 | 새 연산(새 모델 구조) 지원이 늦음 |
| 대량 배포 용이 | 칩 종류마다 파일을 따로 관리 |
| 정밀도 최적화(양자화 통합) | 품질 검증 책임이 늘어남 |

**한 줄 판단 기준**: 모델과 하드웨어가 **자주 안 바뀌고**, 지연 예측성이 중요하면 AOT. 모델을 매주 바꾸며 실험 중이면 JIT/eager.

## 7. 직접 만져보기

공개 도구의 공개 단계만 적었어요. 버전마다 플래그가 조금씩 다르니 공식 문서를 함께 보세요.

### A. ONNX → TensorRT 엔진 빌드 (NVIDIA GPU)

```bash
# 1) 작은 모델을 ONNX로 내보내기 (Hugging Face Optimum)
pip install "optimum[exporters]" onnx
optimum-cli export onnx --model gpt2 gpt2_onnx/

# 2) TensorRT 엔진 빌드 (TensorRT 설치 시 포함된 trtexec)
trtexec --onnx=gpt2_onnx/model.onnx \
        --saveEngine=gpt2_fp16.engine \
        --fp16 \
        --verbose 2>&1 | tee build.log

# 3) 빌드 로그에서 융합된 레이어/지원 안 되는 노드 확인
grep -iE "fused|unsupported|fallback" build.log
```

**관찰 포인트**: 빌드에 시간이 걸리고, 같은 엔진을 다른 세대 GPU에서 로드하면 경고나 실패가 날 수 있어요. 그게 "칩에 맞춘 번역본"의 의미예요. LLM 전용으로는 TensorRT-LLM의 체크포인트 변환 → `trtllm-build` 흐름이 같은 원리예요.

### B. ONNX Runtime에서 EP 분배와 폴백 보기

```python
import onnxruntime as ort
so = ort.SessionOptions()
so.log_severity_level = 1   # 노드 배치 정보 보기
sess = ort.InferenceSession(
    "gpt2_onnx/model.onnx", so,
    providers=["CUDAExecutionProvider", "CPUExecutionProvider"],
)
print(sess.get_providers())
```

로그에서 어떤 노드가 CPU로 배정됐는지 보이면, 그게 바로 폴백 후보예요.

### C. llama.cpp: 변환 → 양자화 → 백엔드별 실행

```bash
# 백엔드를 골라 빌드 (예: CUDA / Metal은 macOS에서 기본)
cmake -B build -DGGML_CUDA=ON && cmake --build build -j

python convert_hf_to_gguf.py /path/to/hf-model --outfile model-f16.gguf
./build/bin/llama-quantize model-f16.gguf model-Q4_K_M.gguf Q4_K_M

# -ngl: 몇 개 층을 GPU에 올릴지. 0이면 전부 CPU → "폴백"을 일부러 체험
./build/bin/llama-bench -m model-Q4_K_M.gguf -ngl 99
./build/bin/llama-bench -m model-Q4_K_M.gguf -ngl 16
./build/bin/llama-bench -m model-Q4_K_M.gguf -ngl 0
```

`-ngl` 값을 줄이면 일부 층이 CPU로 넘어가면서 TPS가 계단식으로 떨어지는 걸 볼 수 있어요. 그림 2의 지그재그를 직접 만드는 실험이에요.
