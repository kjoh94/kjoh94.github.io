> **한 줄 핵심** — 모델은 매 바퀴마다 "다음 토큰 후보 전부의 확률"만 내놓아요. **그중 무엇을 실제로 고를지는 샘플링 규칙**(temperature, top_k, top_p, max_tokens, stop)이 정해요. 같은 모델이라도 이 규칙에 따라 성실한 모범생도, 엉뚱한 시인도 될 수 있어요.

## 0. 큰 루프에서 어디에 꽂히나

## 1. 비유: 메뉴판과 주문 습관

모델이 내놓는 확률 분포는 **식당 메뉴판에 붙은 인기도 스티커**와 같아요. "김치찌개 57%, 된장찌개 21%, 비빔밥 13% …"

이제 손님(샘플링 규칙)이 주문해요.

- **Greedy 손님**: 무조건 1등 메뉴만 시켜요. 매일 김치찌개. 안전하지만 지루해요.
- **Temperature 낮은 손님**: 거의 1등만, 가끔 2등.
- **Temperature 높은 손님**: 인기도 차이를 덜 신경 써서 별별 메뉴를 다 시켜 봐요. 가끔 "민트초코 순댓국"처럼 메뉴판 구석의 이상한 걸 고르기도 해요.
- **top_k 손님**: "상위 k개 메뉴 안에서만 고를게요."
- **top_p 손님**: "인기도를 위에서부터 더해서 90%가 될 때까지의 메뉴 안에서만 고를게요."
- **max_tokens / stop**: "최대 몇 접시까지만", "디저트 나오면 끝".

## 2. 출발점: 로짓 → softmax → 확률

모델의 마지막 층은 어휘 크기(예: 15만 개)만큼의 **로짓(logit)**, 즉 정규화 안 된 점수를 내놓아요. 이걸 softmax로 확률로 바꿔요.

```text
p_i = exp(z_i / T) / Σ_j exp(z_j / T)      (T = temperature)
```

예를 들어 "오늘 날씨가 정말 ___" 다음 후보 5개만 보면(나머지 수만 개는 무시할 만큼 작다고 가정),

| 후보 | 로짓 z | T = 1.0 확률 |
|---|---|---|
| 맑아요 | 3.0 | **57.3%** |
| 흐려요 | 2.0 | 21.1% |
| 비가 | 1.5 | 12.8% |
| 좋아요 | 1.0 | 7.8% |
| 바나나 | -1.0 | 1.0% |

---

## 3. Temperature: 분포를 뾰족하게, 혹은 평평하게

T는 로짓을 나누는 숫자예요. **T가 작으면 차이가 확대**되어 1등이 독식하고, **T가 크면 차이가 축소**되어 분포가 평평해져요.

같은 로짓에 T만 바꿔 볼게요.

| 후보 | T = 0.2 | T = 1.0 | T = 1.5 |
|---|---|---|---|
| 맑아요 | **99.3%** | 57.3% | 45.2% |
| 흐려요 | 0.7% | 21.1% | 23.2% |
| 비가 | 0.1% | 12.8% | 16.6% |
| 좋아요 | ~0% | 7.8% | 11.9% |
| 바나나 | ~0% | 1.0% | **3.1%** |

- T = 0.2: 사실상 greedy. 100번 뽑으면 99번 "맑아요".
- T = 1.5: "바나나"가 1% → 3.1%로 세 배. 토큰 100개짜리 답이라면, 매 바퀴 이런 "구석 후보"가 뽑힐 기회가 100번 생겨요. 한 번이라도 엉뚱한 토큰이 뽑히면 그 뒤 문장 전체가 그 방향으로 끌려가요.

> **T = 0**은 수식상 0으로 나누기라서, 대부분의 엔진은 "T = 0 → greedy(argmax)"로 특별 취급해요.

## 4. top_k와 top_p: 후보를 잘라 내는 두 가지 가위

temperature가 "분포의 모양"을 바꾼다면, top_k·top_p는 **"후보 명단"을 잘라요.** 잘라 낸 뒤 남은 후보끼리 확률을 다시 100%로 맞춰(재정규화) 뽑아요.

### top_k: 상위 k개만

T = 1.0, **top_k = 2**라면 "맑아요, 흐려요"만 남아요.

```text
맑아요 57.3 / (57.3 + 21.1) = 73.1%
흐려요 21.1 / 78.4          = 26.9%
```

문제는 k가 **고정**이라는 점이에요. 모델이 확신하는 순간(1등 99%)에도 k개를 남기고, 모델이 헷갈리는 순간(후보 50개가 비슷비슷)에도 k개만 남겨요.

### top_p (nucleus): 누적 확률 p까지만

T = 1.0, **top_p = 0.9**라면 위에서부터 더해 가요.

```text
맑아요 57.3%   누적 57.3%
흐려요 21.1%   누적 78.4%
비가   12.8%   누적 91.2%  ← 90%를 넘는 첫 지점, 여기까지 포함
좋아요, 바나나 → 잘림
재정규화: 맑아요 62.8% / 흐려요 23.1% / 비가 14.0%
```

top_p는 **분포 모양에 따라 후보 수가 자동으로 바뀌어요.** 모델이 확신하면 1~2개, 헷갈리면 수십 개. 그래서 요즘 기본값은 top_p 쪽이 더 흔해요.

### temperature와 함께 쓰면

T = 1.5, top_p = 0.9라면 누적이 45.2 → 68.4 → 85.0 → **96.9**%라서 "좋아요"까지 4개가 남아요. **T를 올리면 top_p로 남는 후보도 늘어난다**는 점, 기억하세요. 대부분의 엔진은 temperature를 먼저 적용하고, 그다음 top_k/top_p로 자르는 순서를 써요(엔진마다 순서·세부 구현은 다를 수 있어요).

## 5. max_tokens와 stop: 언제 멈출까

Decode 루프는 스스로 멈출 이유가 없어요. 멈춤 조건은 세 가지예요.

| 조건 | 의미 | 예시 |
|---|---|---|
| EOS 토큰 | 모델이 "끝" 토큰을 골랐을 때 | `<|eot_id|>`, `</s>` |
| `stop` 문자열 | 출력에 특정 문자열이 나타나면 | `"\n\nUser:"`, `"```"` |
| `max_tokens` | 생성 토큰 수 상한 | 256 |

- `max_tokens`가 너무 작으면 → 답이 **문장 중간에서 뚝** 끊겨요("결론적으로, 가장 중요한 것은").
- 너무 크고 stop이 없으면 → 모델이 혼자 "User: …" 다음 질문까지 지어내며 **자문자답**을 해요. 비용(토큰)과 시간도 그만큼 늘어요.
- 0편의 공식으로 보면, 총 응답 시간 ≈ TTFT + 출력 토큰 수 / TPS니까 **max_tokens는 최악의 경우 지연의 상한**이기도 해요. 30 tok/s에서 max_tokens 2,048이면 최악 약 68초예요.

## 6. 실패 장면: 같은 질문을 세 번

같은 모델, 같은 질문을 세 가지 설정으로 각각 세 번씩 물어볼게요. (출력은 경향을 보여 주는 **예시**예요.)

> **질문**: "새로 연 동네 빵집 이름을 하나 지어 줘."

**① Greedy (T = 0)**

```text
1회: "햇살 베이커리"
2회: "햇살 베이커리"
3회: "햇살 베이커리"
```
→ 완벽히 재현되지만 **세 번 다 똑같아요.** 아이디어가 필요한 과제엔 실패예요. 긴 글에선 같은 표현을 계속 반복하는 **반복 루프**에 빠지기도 해요.

**② 적당히 (T = 0.8, top_p = 0.9)**

```text
1회: "골목 끝 오븐"
2회: "아침 반죽"
3회: "햇살 한 조각"
```
→ 다양하고 다 그럴듯해요.

**③ 과하게 (T = 1.8, top_p = 1.0)**

```text
1회: "밀가루 은하 철도 999번지"
2회: "빵빵 Croissant 도서관 ㅋ"
3회: "새벽三時 반죽의 노래, 그리고 바나나"
```
→ 창의적이라기보다 **문법과 의미가 흔들려요.** 다른 언어 토큰이 섞이고, 엉뚱한 단어가 끼어들어요.

이번엔 반대 방향의 질문이에요.

> **질문**: "17 × 23은?"

| 설정 | 3번 결과 | 판정 |
|---|---|---|
| Greedy | 391 / 391 / 391 | ✅ 정답, 재현 가능 |
| T = 0.8 | 391 / 391 / 381 | ⚠️ 가끔 틀림 |
| T = 1.8 | 391 / 401 / "약 400" | ❌ 신뢰 불가 |

**과제에 따라 정답 설정이 반대**라는 게 핵심이에요. 사실·계산·코드·JSON은 낮은 T, 브레인스토밍·카피·소설은 중간 T.

### 잘못된 직관: "temperature를 올리면 모델이 더 똑똑하게(창의적으로) 생각한다"

temperature는 모델의 **생각(로짓 계산)** 엔 손도 대지 않아요. 이미 계산된 확률 막대의 **모양만** 바꿀 뿐이에요. T를 올리면 "모델이 새 아이디어를 떠올리는" 게 아니라, **모델 스스로도 가능성이 낮다고 본 후보를 더 자주 뽑는** 거예요. 그래서 창의성과 오류가 같은 손잡이에 붙어 있어요.

비슷한 오해로 "T = 0이면 항상 결과가 똑같다"도 있어요. 대부분 같지만, 배칭·병렬 연산의 부동소수점 순서 차이 때문에 엔진·하드웨어에 따라 아주 가끔 달라질 수 있어요. 완전 재현이 필요하면 seed 고정 + 동일 환경까지 맞춰야 해요.

## 7. 정상 장면: 과제별 추천 출발점

| 과제 | temperature | top_p | top_k | max_tokens | stop |
|---|---|---|---|---|---|
| 사실 Q&A, 계산 | 0 ~ 0.2 | 1.0 | — | 짧게(256) | 필요 시 |
| 코드 생성 | 0 ~ 0.3 | 0.95 | — | 넉넉히(1,024+) | ```` ``` ```` 등 |
| JSON/구조화 출력 | 0 | 1.0 | — | 스키마에 맞게 | `}` 이후 |
| 요약·번역 | 0.3 ~ 0.5 | 0.9 | — | 원문 비례 | — |
| 일반 채팅 | 0.6 ~ 0.8 | 0.9 | 40 | 512~1,024 | 대화 구분자 |
| 브레인스토밍·창작 | 0.9 ~ 1.1 | 0.95 | — | 넉넉히 | — |

(모델마다 학습 시 권장값이 다르니, 모델 카드의 추천 설정을 먼저 확인하세요.)

추가로 알아 두면 좋은 손잡이들도 있어요.

- **repetition / frequency / presence penalty**: 이미 나온 토큰의 로짓을 깎아 반복을 줄여요. 너무 세면 꼭 필요한 단어(변수명, 고유명사)까지 피해요.
- **min_p**: 1등 확률의 일정 비율(예: 5%) 미만 후보를 잘라요. top_p의 대안으로 llama.cpp 등에서 쓰여요.
- **seed**: 같은 seed + 같은 설정이면 같은 샘플링 결과(같은 환경 전제).

## 8. 트레이드오프 표

| 손잡이 | 올리면(키우면) 얻는 것 | 대신 잃는 것 |
|---|---|---|
| temperature ↑ | 다양성, 신선함 | 정확성, 일관성, 재현성 |
| top_p ↑ (1.0에 가깝게) | 후보 폭 넓어짐 | 꼬리의 엉뚱한 토큰 위험 |
| top_k ↑ | 다양성 | 확신 상황에서도 잡음 후보 유지 |
| max_tokens ↑ | 잘림 없음 | 최악 지연·비용 증가, 자문자답 위험 |
| stop 많이 | 깔끔한 종료 | 정상 내용에서 오조기 종료 위험 |
| repetition penalty ↑ | 반복 감소 | 필요한 반복까지 억제 |

샘플링은 **계산 비용이 거의 0**이에요. 수만 개 막대를 정렬하고 자르는 건 모델 한 바퀴 연산에 비하면 아주 작아요. 그래서 TPS는 거의 안 바뀌지만, **출력 길이(max_tokens, stop)** 를 통해 총 응답 시간은 크게 바뀔 수 있어요.

같은 명령을 세 번씩 돌려 6절의 실험을 직접 재현해 보세요. Ollama에서는 `num_predict`가 max_tokens 역할이고, `"stop": ["\n"]`도 options에 넣을 수 있어요.

### B. vLLM(OpenAI 호환 API)에서 top_p·stop·logprobs 보기

```bash
vllm serve Qwen/Qwen2.5-1.5B-Instruct

curl -s http://localhost:8000/v1/completions \
  -H "Content-Type: application/json" -d '{
    "model": "Qwen/Qwen2.5-1.5B-Instruct",
```

`logprobs: 5`로 상위 5개 후보의 로그 확률을 받아, `exp()`로 바꾸면 이 글의 확률 막대를 **실제 모델 숫자로** 그려 볼 수 있어요. temperature를 0.2, 1.0, 1.5로 바꿔 가며 표를 만들어 보세요.

### C. Hugging Face transformers로 막대 직접 계산

```python
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM
name = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(name)
model = AutoModelForCausalLM.from_pretrained(name)

ids = tok("오늘 날씨가 정말", return_tensors="pt").input_ids
logits = model(ids).logits[0, -1]
for T in [0.2, 1.0, 1.5]:
    p = torch.softmax(logits / T, dim=-1)
    top = torch.topk(p, 5)
    print(T, [(tok.decode(i), round(v.item()*100, 1)) for v, i in zip(top.values, top.indices)])
```
