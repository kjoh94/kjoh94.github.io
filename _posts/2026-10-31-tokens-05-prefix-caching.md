> **한 줄 핵심** — 챗봇·에이전트·RAG 요청은 대부분 **똑같은 긴 앞부분**(시스템 프롬프트, 도구 설명, 이전 대화)으로 시작해요. 그 앞부분의 KV 캐시를 저장해 두고 다음 요청에서 그대로 꺼내 쓰면, **Prefill이 거의 사라지고 TTFT가 확 줄어요.**

## 0. 큰 루프에서 어디에 꽂히나

![Prefix 재사용이 꽂히는 자리](/assets/img/posts/tokens-05-prefix-caching/fig01.jpg)

*그림 1. Prefix 재사용은 Prefill 입구에 꽂혀요. Prefill을 시작하기 전에 "이 앞부분, 전에 본 적 있나?"를 캐시에서 찾고, 일치하는 만큼은 건너뛰고 나머지 꼬리만 계산해요.*

---

## 1. 비유: 회사 서식 문서

결재 서류의 머리말(회사명, 결재 라인, 규정 문구)은 매번 똑같아요. 매번 새로 타이핑하지 않고 서식 파일을 복사한 뒤 본문만 써요. Prefix 재사용이 정확히 그거예요. 4편의 KV 캐시가 "한 요청 안에서의 메모"라면, 이번 편은 **요청과 요청 사이에서 메모를 돌려 쓰는 것**이에요.

---

## 2. 얼마나 똑같은가

```text
요청 A: [너는 친절한 고객센터 상담원이다. 규칙 1 … 규칙 50] + "환불 어떻게 해요?"
요청 B: [너는 친절한 고객센터 상담원이다. 규칙 1 … 규칙 50] + "배송 언제 와요?"
         └──────────────── 2,000토큰, 완전히 같음 ────────────────┘
```

![공통 앞부분을 공유하는 세 요청](/assets/img/posts/tokens-05-prefix-caching/fig02.jpg)

*그림 2. 금색 공통 앞부분(2,000토큰)은 한 번만 계산하고, 요청 A·B·C는 그 KV를 그대로 가져다 써요. 새로 Prefill하는 건 색칠된 짧은 꼬리뿐이라 Prefill 계산이 약 1/100이 돼요.*

실제 서비스에서 이런 패턴은 아주 흔해요.

| 패턴 | 공통 앞부분 | 바뀌는 꼬리 |
|---|---|---|
| 챗봇 | 시스템 프롬프트 | 사용자 질문 |
| 멀티턴 대화 | 이전 턴 전체 | 이번 턴 |
| 에이전트 | 시스템 + 도구 스키마 수천 토큰 | 관찰 결과 |
| few-shot | 예시 10개 | 새 입력 |
| 같은 문서 Q&A | 긴 문서 | 질문 |

---

## 3. 어떻게 찾나: 블록 해시 체인

4편의 페이지 블록(16토큰)을 다시 꺼내요. 각 블록에 **열쇠(해시)** 를 붙이는데, 그 열쇠에 **앞 블록의 열쇠**를 섞어요.

```text
h1 = hash(        블록1 토큰들)
h2 = hash(h1,     블록2 토큰들)
h3 = hash(h2,     블록3 토큰들)
```

![블록 해시 체인](/assets/img/posts/tokens-05-prefix-caching/fig03.jpg)

*그림 3. 저장된 요청과 새 요청을 블록 단위로 비교해요. 블록 1–3의 열쇠가 같으면 그 KV(48토큰)를 재사용하고, 처음 달라지는 블록 4부터 새로 Prefill해요.*

왜 앞 열쇠를 섞을까요? 어텐션 때문이에요. 블록 3의 KV는 블록 1, 2를 보고 계산돼요. 블록 3의 토큰이 같아도 **앞이 다르면 KV가 달라요.** 체인 해시는 "여기까지의 앞부분 전체가 같다"를 열쇠 하나로 보장해요.

엔진은 새 요청을 받으면 블록 열쇠를 앞에서부터 해시 테이블에서 찾고, 처음 실패하는 지점까지를 재사용해요. 해당 블록은 참조 카운트가 올라가 여러 요청이 동시에 읽어요(복사 없음).

## 4. 여러 갈래를 나무로: Radix tree

SGLang의 RadixAttention은 같은 아이디어를 **나무**로 관리해요.

![Radix tree로 관리하는 프리픽스](/assets/img/posts/tokens-05-prefix-caching/fig04.jpg)

*그림 4. 뿌리(시스템 프롬프트)에서 대화·도구 호출이 가지로 뻗어요. 뿌리에 가까운 노드일수록 많은 요청이 공유하니 오래 남기고, 메모리가 차면 오래 안 쓴 잎부터 내보내요.*

멀티턴 대화에서 특히 좋아요. 5턴째 요청은 1–4턴이 이미 나무에 있으니 5턴의 꼬리만 Prefill하면 돼요. 에이전트가 같은 지점에서 여러 도구 결과로 갈라질 때도 가지만 늘어나요.

---

## 5. 효과: TTFT

![캐시 미스와 히트의 TTFT](/assets/img/posts/tokens-05-prefix-caching/fig05.jpg)

*그림 5. 예시 수치예요. 2,000토큰 공통 앞부분에서 첫 요청은 1.2초, 두 번째부터는 0.09초. 멀티턴 5턴째도 재사용하면 2.4초가 0.12초가 돼요. TPOT(토큰 사이 간격)는 거의 그대로예요.*

정리하면,

- **줄어드는 것**: Prefill 계산 → TTFT, 서버 전체의 계산량(=비용)
- **그대로인 것**: Decode 속도(TPOT). 재사용된 KV도 매 바퀴 읽긴 해야 하니까요.
- 상용 API가 "캐시된 입력 토큰은 할인"하는 가격표를 두는 것도 같은 원리예요.

---

## 6. 실패 모드: 캐시를 깨는 프롬프트

재사용은 **맨 앞부터 연속으로 같아야** 해요. 토큰 하나만 달라도 그 뒤 전부가 미스예요.

![캐시를 깨는 순서와 살리는 순서](/assets/img/posts/tokens-05-prefix-caching/fig06.jpg)

*그림 6. 맨 앞에 현재 시각을 넣으면 매 요청 첫 블록이 달라져 해시 체인 전체가 깨져요. 변하지 않는 규칙을 앞에, 변하는 값은 뒤에 두면 거의 전부 재사용돼요.*

| 함정 | 왜 깨지나 | 고치는 법 |
|---|---|---|
| 맨 앞에 타임스탬프·요청 ID | 첫 블록부터 다름 | 뒤로 옮기기 |
| 도구 목록 순서가 매번 섞임 | 중간부터 다름 | 정렬해서 고정 |
| 공백·줄바꿈 미세 차이 | 토큰이 다름 | 템플릿 한 곳에서 생성 |
| 대화 중간에 요약 끼워 넣기 | 그 지점부터 전부 미스 | 요약은 드물게, 끝 쪽에 |
| 사용자 이름을 시스템 프롬프트 앞에 | 사용자별로 갈라짐 | 공통 → 개인 순서 |
| 메모리 부족으로 너무 빨리 내보냄 | 히트율 하락 | 캐시 비율·LRU 설정 확인 |

한 가지 보안 메모도 있어요. 공유 캐시는 "다른 사람이 같은 앞부분을 보냈는지"가 TTFT로 새어 나갈 수 있어요(타이밍 사이드채널). 여러 고객이 쓰는 서버는 테넌트별로 캐시를 나누기도 해요.

---

## 7. 얻는 것과 내주는 것

| 얻는 것 | 내주는 것 |
|---|---|
| 반복 앞부분의 TTFT·비용 급감 | 캐시를 오래 붙잡는 메모리 |
| 멀티턴·에이전트가 길어져도 덜 느려짐 | 해시·참조 카운트·내보내기 정책 관리 |
| 같은 서버의 처리량 증가 | 프롬프트 설계 규율(앞부분 고정) |

## 직접 만져보기

```bash
vllm serve Qwen/Qwen2.5-1.5B-Instruct --enable-prefix-caching
```

긴 시스템 프롬프트를 붙인 같은 요청을 두 번 보내고 첫 토큰 시간을 비교해 보세요. 그다음 시스템 프롬프트 맨 앞에 현재 시각을 넣어 다시 재 보면, 캐시가 깨지는 순간이 숫자로 보여요.
